## 1. 产品形态判断

- **产品类型与核心任务**：浏览器内实时视觉交互应用。用户通过普通摄像头，让手指控制 3D 光束粒子的牵引、聚合、分散和波动。
- **核心交互**：连续手势输入与即时视觉反馈。使用端侧手部关键点模型；无 LLM 对话、动态工具规划或生成式 Agent。
- **开发路径**：纵向切片。第一阶段同时完成最小界面、真实手部识别和粒子响应；终端专属能力均在浏览器，不额外创建后端。
- **当前阶段范围**：桌面 Web、单人单手、一种光束形态、四种核心手势、相对纵深实验控制、镜像预览、必要状态提示、鼠标演示和错误恢复。详见[第一阶段开发文档](第一阶段技术开发文档.md)。
- **第一阶段产物定位**：可继续扩展的正式产品第一条切片。先证明摄像头交互可用，后续沿用同一应用完善视觉。
- **用户需提供**：可用摄像头；真机验收时允许浏览器使用摄像头并亲自操作。当前不需要 API Key、云账号、数据库或付费模型服务。

## 3. 触发的按需模块

| 模块 | 触发需求 | 第一阶段处理 |
|---|---|---|
| Three.js | 3D 空间内的粒子与光束 | 引入；批量粒子几何、自定义发光材质、透视相机 |
| MediaPipe Hand Landmarker（`@mediapipe/tasks-vision`） | 摄像头识别手指 | 引入；本地视频帧推理，单手模式 |
| Web Worker | 识别不能阻塞持续绘制 | 引入；仅一个在途检测，过时结果丢弃 |
| 浏览器摄像头 API | 获取实时视频输入 | 引入；明确点击开启、只请求视频、可彻底关闭 |
| Vitest | 手势、力场、消息契约等可脱离摄像头测试 | 引入；合成关键点、确定性时钟与随机种子 |
| Playwright | 页面生命周期、交互与错误状态验证 | 引入开发测试依赖；模拟视频结果与真实摄像头验收分别记录 |
| 本地设置存储 | 保留质量档位及操作偏好 | 引入轻量 localStorage；校验、版本、损坏回退，不保存图像 |

不触发关系数据库、ORM、迁移工具、RAG、SSE、任务队列、对象存储或鉴权系统。持续动画不是可恢复的长耗时业务任务；关闭页面后无需恢复某一帧粒子的位置。

## 4. 偏离或暂缓的默认方案

| 手册默认方案 | 本项目决定 | 原因、影响及重新评估条件 |
|---|---|---|
| Python 3.11 + FastAPI + Pydantic | 当前不引入；使用浏览器模块与运行时校验 | 无服务器业务，视频留在端侧，减少服务与数据传输；出现账户、共享作品或服务端生成需求后重新评估 |
| Next.js + App Router | Vite + 原生 TypeScript 单页应用 | 单一实时画布，无 SSR 或业务路由需求；保留独立识别/交互/渲染模块；未来出现多页面内容、SEO 或账户平台再评估应用外壳 |
| Tailwind CSS | 原生 CSS 与集中设计变量 | 初期只有画布与少量控件；无需额外样式框架，后续复杂页面与统一组件体系出现时再评估 |
| Node.js 22 LTS | 先使用本机 Node.js 24.19.0，待安装构建验证 | 不改动本机全局运行时。若具体依赖不兼容，项目内固定一个兼容版本并记录原因，不影响其他项目 |
| pytest | Vitest + Playwright | 当前没有 Python 产品代码，采用相应技术栈的等价测试工具 |
| `/api/v1`、后端目录、SSE | 不创建 | 无远程业务 API，以可独立测试的模块接口与 Worker 契约替代；引入后端时再设计 API |
| 真实 Key 冒烟 | 真实摄像头 + 真实端侧模型冒烟 | 不使用云推理 Key；必须验证模型加载、实际识别、粒子响应、延迟和资源释放 |
| 正式视觉系统、复杂 Bloom 与形态库 | 核心链路验收后完善 | 第一阶段仍包含能分辨光束和四种效果的基础视觉，不影响核心交互验收 |
| 上线部署 | 当前仅本地运行 | 用户本次请求为文档补齐；后续部署阶段再读取部署手册并处理平台要求 |

以上适配由手册“纯端侧、实时音视频、空间画布”的适用边界触发，不改变原方案的 Web 终端或本地视频处理承诺，也未新增订阅费用与外部业务平台。

## 实施补充记录｜2026-09-14

第一阶段产品代码已建立于 `finger-light/`，Git 已初始化；环境与依赖以产品 README、package-lock.json 为准。

本轮确认的必要适配：MediaPipe 0.10.32 的 WASM 脚本加载与模块 Worker 不兼容，故使用 esbuild 生成经典 Worker；模型推理采用 CPU/WASM，初始 15 Hz，3D 渲染仍使用 GPU。软件图形环境的 GPU 模型初始化曾卡住，CPU 路径已经真实模型与合成视频验证。此替代不上传数据、不增加费用、不改变交付终端。

新增开发依赖 esbuild（构建 Worker）、Prettier（源文件格式）、@types/node（测试与构建脚本类型）。Vitest 升级至 4.1.11，修复安装时审计发现的问题，规则测试重新通过。未启用业务服务器或后续阶段模块。

当前状态为“可运行，阶段验收未全部完成”。真人手势与端到端延迟待操作验证；五分钟稳定性自动化测试曾超时，不能据此宣称性能达标。具体检查见 `finger-light/docs/第一阶段验收记录.md`。
